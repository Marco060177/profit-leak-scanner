# Data Core D1 — additive foundation

D1 adds identity, raw evidence, mapping, sync, coverage and fixed-precision Money contracts only. Existing Shopify GraphQL → in-memory aggregate → Profit Engine → legacy projection remains the sole runtime economic authority. No route, background fetch, billing, tax formula or UI reads the new tables.

## Ownership and identity

All new tenant rows carry `accountId`; source rows carry `channelConnectionId`. Composite foreign keys to `ChannelConnection(id, accountId)` reject cross-account attachment. Marketplace-scoped rows use `marketplaceId`; no-marketplace rows use the non-null `marketplaceScopeKey = '@none'`. For marketplace rows, the key must equal the marketplace ID. SQLite CHECK constraints enforce this equality and unique indexes then enforce logical singleton identity despite SQLite allowing repeated NULLs in unique keys. No seller SKU/barcode is unique or used to auto-link channels. Candidate decisions are audit history; no matching engine runs in D1.

Raw snapshots are identified by source identity plus SHA-256 of the *plain* bytes and stored in bounded encrypted chunks. The service requires an encryptor callback; the integration fixture uses an identity callback only in its disposable test database. A reviewed, non-identity encryption adapter is a mandatory D3 activation prerequisite; no production writer or default encryptor exists in D1. Each chunk is at most 64 KiB plaintext; each encrypted chunk is bounded to 65 KiB, and a record is at most 2 MiB plaintext. Oversized input is rejected before any transaction/checkpoint. SQLite triggers prohibit updates/deletes of raw records/chunks and mapping decisions. Retention deletion requires a later reviewed lifecycle/migration, not a routine delete.

`SourceReference` has a DB-enforced FK to raw evidence and a typed target kind/key. Future target tables do not exist yet: target-key existence is deliberately not represented as a fictitious polymorphic FK. D2/D3 must validate target ownership and attach concrete FKs or an explicit registry. `NormalizationRun` is unique by raw snapshot, mapping version and revision. Activated MappingVersion and CurrencyPolicyVersion semantic fields are guarded by SQLite triggers; activation/deactivation are the only service transitions.

Money is signed Int64 atoms, bounded scale 0–12, uppercase three-letter ISO-style currency code. The contract uses only BigInt and explicit, version-referenced rounding; no canonical-to-Number conversion exists in D1. Currency exponent source, tolerance and residual policy are persisted/versioned, but current Shopify formulas are unchanged.

The D1 authority-scope type records one key/family, provisional source, actual source and actual coverage. It selects either provisional or actual; unknown coverage blocks. D2 must link Orders/Finances within this scope and must never sum both blindly.

SyncSlice uses a deterministic key and non-null marketplace scope. `CoreChannelAuthorization` is the D1 sync authorization epoch, separate from existing Shopify auth; a future connector must update it with a never-reused version on credential change before using these primitives. Lease claim/reclaim uses conditional updates; disconnected Accounts/channels and authorization-version mismatch fail closed. `SyncSliceEvidence` is an immutable observation for the exact slice/run, raw record and normalization run, with composite tenant-safe foreign keys. Attaching it requires an active slice lease and raw ingestion provenance for that run. The same immutable raw record may be evidenced by multiple slices within its ingestion run. A slice becomes `PREPARED` only when every linked normalization run succeeded for its MappingVersion; an empty page must be represented by explicit raw evidence. Successful normalization cannot be reversed. `completeSyncSlice` rechecks evidence and status inside the same short SQLite transaction that changes the slice to `SUCCEEDED` and advances SyncCheckpoint, with an expected previous slice ID to reject concurrent checkpoint changes. External fetch must occur outside this transaction. Cross-run reuse of an unchanged raw payload needs a separately reviewed observation contract before D3 activation; D1 deliberately fails closed for such reuse. D3 must place its normalization/ledger/coverage effects in that same commit boundary rather than treating D1's preparation marker alone as proof of final economic ingestion. DataCoverage keeps capability separate from quality; reconciliation remains a later axis.

## SQLite deployment and rollback

Migration `20260924170000_data_core_d1_foundation` creates new tables, indexes, CHECK constraints and immutability triggers only. It contains no DROP/ALTER of existing production tables and needs no backfill. After review and backup, run the normal `npx prisma migrate deploy` process before deploying code that references D1 tables; verify `npx prisma migrate status` and the isolated D1 test against a temporary database. D1 has no production caller, so rollback is to stop D1 writers/feature flag and keep the additive tables intact. Do not drop evidence tables or reverse a production migration without separate data-retention approval.

D2 ledger/inventory/tax/FX/reconciliation and D3 Shopify persisted shadow slice are deferred. D1 PASS requires schema validation, isolated migration/constraint tests, tenancy/Shopify/Profit Impact regression suites, TypeScript, lint and a diff containing only additive D1 files.
