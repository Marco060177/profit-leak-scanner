# T9C1 — controlled historical Account AI usage backfill

T9C1 is a manual historical copy, not a runtime quota switch. Legacy `AiUsage(shop, month)` remains the production authority; `AccountAiUsage` is not read or written by AI Advisor. T9C2 shadow writes are not implemented or automatically authorized by a T9C1 PASS.

Prerequisite: T9B must classify every source row. Only its `READY` rows are eligible. Its collision, duplicate-normalized-shop, invalid-value, invalid-domain and unsafe-mapping classifications are never merged, summed or migrated. A read-only T9B run on the *same intended database* should precede manual apply. Do not confuse the local development SQLite file with Render's database.

`npm run tenancy:t9c1:ai-usage-backfill` is read-only dry-run. It reports aggregate source reasons, eligible groups, how many target rows would be created, already match, or conflict. `npm run tenancy:t9c1:ai-usage-backfill -- --apply` explicitly requests a transaction. The transaction repeats T9B classification and target comparison; **any unsafe source row or differing target count blocks the entire apply with zero writes**. Safe existing exact matches are no-ops; missing target rows are created with the exact legacy count. There is no blind increment, overwrite, tenant bootstrap or legacy mutation. CLI output contains counts only, not shop/Account/connection identifiers.

`periodKey` is exactly the legacy UTC calendar month `YYYY-MM`, **not** a Shopify billing cycle. The transaction prevents partial commits on error. Repeating apply against unchanged legacy data is idempotent. If legacy quota changes after this point-in-time copy, a later run sees a conflict and does not overwrite the target; reconciliation requires separate review. Recovery means leaving the legacy authority in place and reviewing the affected target rows under an approved policy, not automatically deleting or aggregating them. No production/Render apply is part of this coding batch.
