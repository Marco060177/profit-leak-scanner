# T10 — notification Account ownership

All existing notification preference fields are generic Account settings. `NotificationPreferences.accountId` is the durable owner; `shop` is nullable Shopify compatibility/provenance. A single canonical preference row is linked to each Account. If multiple legacy Shopify rows map to one Account, **every** recipient, enable switch, severity switch, report day/hour, timezone and language must match exactly. Conflicts are not merged or resolved automatically.

`NotificationDelivery.accountId` is the durable owner. `channelConnectionId` attributes Shopify-origin reports and alerts; the composite foreign key ensures the channel belongs to the Account. A null channel is reserved for future account-wide delivery. Historical rows keep attribution after a channel becomes DISCONNECTED. Existing `shop` and deduplication keys remain unchanged for Shopify compatibility. No Amazon notification producer is introduced.

Authenticated UI routes pass the verified tenant. Shopify webhook shops are verified by Shopify; cron and delivery jobs begin with persisted rows and use a non-creating mapping lookup. An unsafe or missing mapping never creates an Account or ChannelConnection. The scheduler scans Account preferences and active Shopify mappings, then runs the existing per-shop report calculation. The send worker skips unattributed or disconnected-channel deliveries rather than sending them without verified ownership. Existing billing checks remain in place.

## Production rollout gate

Do not run `--apply` against production merely because the script exists. First deploy the additive schema migration in a controlled maintenance window, while the old application remains active and the notification cron is paused. Run `npm run tenancy:t10:notification-backfill` against the target database and inspect the aggregate, PII-free report. `CONFLICT`, `MISSING_MAPPING`, and `UNSAFE_MAPPING` must all be zero. Resolve any such record through an explicit operator/product decision; do not guess, create tenant records, or proceed with the new runtime. Then run `npm run tenancy:t10:notification-backfill -- --apply` against the same database. Rerun the dry-run and apply to verify `updated: 0` and `READY`. Deploy the T10 runtime, resume cron, and verify preference UI, one Shopify weekly report and one alert delivery without sending test mail during migration. No automatic startup backfill occurs.

The tool does not modify production unless explicitly run with `--apply`. The migration adds nullable ownership and retains all old shop rows. A login/webhook can safely adopt identical legacy preferences if ownership is verified; conflicts fail closed. SHOP_REDACT deletes unowned legacy preferences and Shopify deliveries as before, removes only the shop provenance from an Account-owned preference, and conditionally disconnects that verified Shopify source so it cannot recreate notifications. Full Account deletion remains T11.
