# Data Core D2A — persisted order history

D2A adds stable Account/Channel/Marketplace-scoped order and order-item identities with append-only revisions. Shopify's existing in-memory GraphQL → Profit Engine pipeline remains the sole runtime economic authority. No production caller uses these tables or the new service.

`NormalizedOrder` is unique by channel, D1 marketplace scope (`@none` when absent), source system and source order key. `NormalizedOrderItem` is unique by order and stable source item key. The service requires `id:<source-id>` or `composite:<versioned-stable-composition>`; callers must supply a genuine source identity, never an array index. Both identity rows are immutable. Revisions are numbered per parent; `(parentId, revision)` and `(parentId, operationKey)` are unique. The service computes a SHA-256 checksum of canonical normalized input and provenance. Exact operation replay returns the existing revision; conflicting replay fails; a changed snapshot/remap requires a new operation key. SQLite unique constraints reject concurrent duplicate revision numbers; a losing transaction must be retried by its caller with the same operation key. No mutable latest pointer is used.

All revisions have real `RawSourceRecord`, `NormalizationRun`, `MappingVersion` and `SyncSliceEvidence` FKs. Composite FKs bind tenant/channel/raw/mapping/normalization revision and the exact slice evidence. Both the service and SQLite BEFORE INSERT triggers require a `SUCCEEDED` normalization, an activated mapping, exact source order identity and the evidence slice's exact marketplace scope derived from the order. The relational trigger checks the account/channel/run/raw/normalization chain for both order and item revisions. D1 already prevents a succeeded normalization from changing status or semantic identity. A future ingester can mark normalization succeeded and persist D2A output within one caller-owned transaction. An item may have no SKU; a non-null SKU requires a same-tenant/channel/scope listing matching the revision's explicit source listing type/key, plus a current `ACCEPT` decision on an `ACCEPTED` candidate for precisely that listing/SKU. The immutable decision ID and source listing identity are saved in the revision; a trigger freezes the cited candidate's semantic identity. SQLite CHECK constraints enforce order scope and quantity bounds; triggers reject updates/deletes of identities and historical revisions and guard item scope. These guards intentionally require a separately reviewed lifecycle operation for future retention cleanup.

Once cited by a D2A revision, `SyncSlice` provenance scope and `ChannelListing` source identity are frozen by SQLite triggers; normal slice status/lease and listing state changes remain possible. `ChannelListing.skuId` remains mutable: a listing may receive its first mapping and later be remapped. SQLite checks a non-null revision SKU against the exact listing/source identity, accepted candidate and current ACCEPT decision, rejecting absent, non-current or ambiguous approval. Historical decision rows cannot change or be deleted; cited candidate account/listing/SKU/rule identity cannot change, while candidate state can evolve. The revision retains its original SKU, decision and source identity after remapping. Exact item replay returns this immutable history before checking current mapping state; new revisions must pass current approval checks. Quantities are nonnegative BigInt atoms with scale 0–12. Exact rescaling never rounds or converts through JS `number`; Int64 overflow is rejected. Money policy from D1 is unchanged. `recordNormalizedOrderRevisionTx` and `recordNormalizedOrderItemRevisionTx` accept a caller-owned `Prisma.TransactionClient` and a trusted tenant context, enabling later short D3 transactions. They do not bootstrap tenants or accept browser-provided ownership as authority. The caller must let service errors abort its transaction. D2A does not change `completeSyncSlice`.

Migration `20260925120000_data_core_d2a_normalized_orders` adds four tables and supporting indexes/triggers, and replaces the applied D1 MappingVersion activation trigger with NULL-safe IS NOT comparisons; it does not backfill or switch authority. Activation identity and mapping semantic fields cannot be reset or changed; deactivatedAt remains mutable. The committed D1 migration is unchanged. Other D1 triggers were inspected: successful normalization compares non-null fields, and decisions/raw/evidence reject updates unconditionally. CurrencyPolicyVersion has an analogous nullable activation comparison but is not referenced or used by D2A; it remains outside this remediation. D2B financial ledger, D2C tax/FX/inventory, D2D reconciliation and D3 connector ingestion remain separate batches.
